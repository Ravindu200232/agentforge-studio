# Next.js + microservices + Supabase scaffold

Stack ID: `nextjs-microservices-supabase`. Everything in `nextjs-supabase.md` describes the frontend half unchanged — same `app/`, same `lib/supabase.js`, same port `3001`, same RLS-first approach to the tables the frontend reads directly. What this stack adds is `supabase/functions/`: one directory per backend service (`supabase/functions/<service-name>/index.ts`), each its own independently deployable Deno function, declared in `supabase/config.toml`.

A function is where logic belongs that a plain RLS-gated table read or write cannot safely express: anything using the service-role key, a third-party secret, a multi-step operation that must be atomic, or a bounded context the specification calls out as its own service. Do not put this logic in a Next.js route handler when the specification calls for a microservice, and do not create a function for something a correct RLS policy already handles — that is just the plain `nextjs-supabase` stack with extra steps. Call a function from the frontend with `supabase.functions.invoke('<name>', ...)`, never a hand-rolled internal URL. Set `verify_jwt` per function in `config.toml` deliberately (public functions need `verify_jwt = false` and their own CORS headers; everything else should require a signed-in user). There is no gateway, no internal port scheme and nothing to proxy: Supabase's own platform routes each function, in development (`supabase functions serve`) and in production alike.

Read `README.template.md`, `supabase/config.toml` and each function's `index.ts` before adding one. Keep functions small and named for the bounded context they own, matching the specification's own service boundaries rather than one function per database table.
