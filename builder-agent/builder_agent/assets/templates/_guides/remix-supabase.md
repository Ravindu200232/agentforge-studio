# Remix + Supabase scaffold

Stack ID: `remix-supabase`. Root `package.json` runs Remix/Vite. `app/root.jsx` provides the document shell; `app/routes/` owns route modules, loaders and actions; `app/tailwind.css` is the styling entry; `lib/supabase.js` owns the request-scoped server client (built fresh per `loader`/`action` from the request's cookies) and any admin (service-role) client; `supabase/migrations/` owns the schema and RLS policies; `test/` holds Vitest tests; `e2e/` holds browser and accessibility tests. Read `README.template.md`, route conventions, `.env.example` and the existing files before editing.

The project's own Supabase project is already connected (`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` in `.env` — created for real by the build setup step, never pasted by hand). Implement every approved screen as a route and every form with actual validated `action` behavior, using Supabase's own surface rather than reinventing it: Postgres tables migrated with `supabase db push` and protected by RLS policies (never the service-role key from anything a browser can trigger without a server check), `supabase.auth.*` for sign-in and sessions (passed to the client only through a loader's small `ENV` object, never by exposing the whole environment), Storage buckets with their own RLS for uploads, and Realtime/Edge Functions only where the specification calls for them. Do not replace the scaffold's Vite/Tailwind/test pipeline with a different framework.

The Studio starts the local Remix preview on an isolated port for this project. It supplies `PORT`; do not hard-code a port and do not stop another project's preview when switching projects.
